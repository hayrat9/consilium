# Исход решения, утверждения и проверка — протокол 1.2

Читать перед R1 для критериев и перед завершением для записанного результата.
`schema_version: "1.1"` описывает совместимую структуру; новый контракт включается
отдельным `protocol_version: "1.2"`. Старые записи без него не мигрировать молча.

## До ранжирования

Для `mode: decision` или `creative` заполнить `decision_contract` до R1:

```json
{"stage": "test", "acceptance_criteria": ["Обратимая проверка без вывода о доказанном спросе"]}
```

Стадии: `explore` — исследовать варианты; `test` — выбрать проверку;
`act` — оценить основания для действия в указанных пределах. Критерии описывают,
что должно пройти порог; рейтинг не заменяет этот порог. Для исследования или
объяснения не требовать выбора варианта и не придумывать коммерческую стадию.

## Итог

`result` содержит `conclusion`, `outcome`, `selected_options`, `basis`, `limits`.
Возможные исходы:

| outcome | Смысл |
|---|---|
| `analysis` | Разбор/объяснение без выбора; для research/explanation |
| `candidate_for_test` | Выбран кандидат для проверки, результат ещё не доказан |
| `action_supported` | Есть основания для действия в заявленных пределах стадии act |
| `no_option_passed` | Ни один вариант не прошёл заранее заданный порог |
| `insufficient_evidence` | Недостаточно данных, чтобы сделать требуемый вывод |

Для выбранного теста/действия `selected_options` — непустой список ID вариантов;
для остальных исходов — пустой. Не выдавать неизвестное за опровергнутое.
Результат `action_supported` не является разрешением на внешнее действие.

```json
{
  "conclusion": "Проверить H1 малым экспериментом; спрос пока неизвестен.",
  "outcome": "candidate_for_test",
  "selected_options": ["H1"],
  "basis": "Тест обратим и проходит ограничение ресурсов.",
  "limits": ["Опубликованные цены не подтверждают покупки."]
}
```

Отсутствие продаж не запрещает выбрать дешёвый тест. Оно не даёт основания назвать
бизнес подтверждённым. «Все варианты не прошли» и «данных недостаточно» — разные
исходы. Лучший по баллам вариант может не пройти порог пригодности.

## Существенные утверждения

В `claims` записывать только тезисы, способные изменить вывод; не размечать каждое
предложение. Поля: `id`, `text`, `kind`, `support`, `evidence_refs`, `limits`.
`kind`: `observation`, `inference`, `hypothesis`, `preference`.
`support`: `supported`, `partial`, `unknown`, `contradicted`; для предпочтения также
`not_applicable`. Это две разные оси: гипотеза может иметь поддержку.

Поддержка/частичная поддержка/противоречие требуют ссылки на конкретное свидетельство
(E-ID, расчёт, локальный артефакт), а не на число согласных ролей. Подтверждение цены
не подтверждает спрос. Непредоставленный опыт автора остаётся сообщением о его опыте.
Просьба усилить правило не означает утверждение, что такого правила нет.

Не использовать VERIFIED как статус всего решения. При конкретной выполненной
проверке добавить `verification` с `method`, наблюдаемым `result`, `checked_at`, `scope`.
Один запуск процедуры не устанавливает успешный результат. Указать, что проверка
не устанавливает. Валидатор проверяет заполненность, не истинность свидетельства.
Если проверяемых тезисов нет, оставить `claims: []` и конкретный
`claims_not_applicable_reason`; это не подходит для выбранного теста/действия.

Существенные пересмотры позиции сохранять в `position_changes`:
`from`, `to`, `reason`, при наличии — новые `evidence_refs`.
Согласие остальных само по себе не основание для смены позиции.

## Опровержение в R2

За проверку отвечает существующая перспектива; отдельный критический контекст выбирать
по риску, без обязательной новой роли. До закрытия R2 сохранить `critical_check`:

- `assumption_and_refutation`: ключевое допущение и реальная попытка его опровергнуть;
- `simpler_or_no_action`: более простой/дешёвый путь или условия отказа от действия;
- `strongest_objection`: сильнейшее оставшееся возражение;
- `response`: содержательный ответ либо признание, что возражение не снято.

«Доказать, что идея плохая» не обязательно возможно: не выдумывать опровержение.
Для дорогого необратимого решения объяснить выбор критического формата. Разные
названия идей не означают разные механизмы: сравнивать действие, барьер, результат
и зависимости. Наличие инструкции R1 не доказывает достаточность генерации.

## Записи взаимной проверки

Когда R2 записан завершённым, `session_check.py` сверяет его с локальными артефактами:

```json
{
  "status": "complete",
  "blinding": "fresh_contexts",
  "mapping_file": "review-packets/mapping.json",
  "reviews_file": "reviews.json",
  "results_file": "review-results.json"
}
```

Пути относительно папки session.json, без выхода из неё и симлинков.
Проверка повторно соединяет mapping+reviews штатным `blind_review.join`, сравнивает
покрытие и содержание оценок с сохранённым results и сверяет оценщиков с составом R2.
Нужны все допустимые оценки, не только строка `status: complete`.
Запуск из другой рабочей папки использует папку session.json, а не текущую cwd.
При вызове из Python передать `check(data, artifact_dir=session_directory)`;
для просмотрщика — `render(data, artifact_dir=session_directory)`.

Если допустимых оценщиков нет, использовать `status: skipped_no_eligible`,
`exception_reason` и `mapping_file`. Валидатор проверяет, что в mapping действительно
нет допустимых назначений. Это не состоявшееся независимое рецензирование.

Если работа закончена до R2, сохранить только реальные раунды, `stop_reason` и итог
`analysis` либо `insufficient_evidence`; не заявлять выбранный/проверенный результат.
Остановка после R2 тоже требует фактически записанных оценок. Не изображать отсутствующие
раунды состоявшимися. Пользовательские ограничения объёма работы сохраняются.

Исторические сессии без нового маркера читаются с предупреждением, без переписывания.
Удаление маркера переводит проверку в совместимый режим и явно предупреждается:
этот помощник не является защитой от подделки. Даже согласованные файлы не доказывают
реальные AI-вызовы, истинность аргументов, спрос или превосходство Consilium.
